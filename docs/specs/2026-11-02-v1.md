# NutriSage v1 spec (overhaul)

Date: 2026-11-02. Status: ready-for-agent. Terms are defined in `GLOSSARY.md`.

## Problem Statement

NutriSage works, but logging is slow and the app has outgrown its first shape. Every new food means
typing it out and waiting for an estimate, Quick Add is a shared 20-item list that forgets things,
and Favorites live in a separate menu. There is no way to build a dish from several ingredients and
log a portion of it by weight, so home cooking gets guessed as one blob. The multiplier only moves
in quarters. A wrongly placed Entry has to be deleted and re-added. There is no Dessert Meal, and I
re-pick the Meal every time. Trends dive to zero on any day I didn't log, and I can't change what
the chart shows.

The platform is also out of step with my other apps. It is plain JS on GitHub Pages with a Python
Lambda in another region. Sign-in means pasting a shared key, so there's no Face ID. It isn't on
ashershores.com. And the local repo copy got corrupted.

## Solution

Rebuild NutriSage on the same stack as HoneyDo and host it at nutrisage.ashershores.com. Members
sign in with Face ID (passkey) on the phone and with a passkey or password on desktop. All
existing asher and aubyn history comes across.

On top of today's features:
- A shared, fuzzy-searchable Library that grows automatically.
- Favorites as a star, with a Quick Add row of starred items, most recently used first.
- A Recipe builder that logs portions by Prepared weight, weighed or estimated from Yield ratios.
- Amounts as any decimal or fraction of any unit.
- Entries that can be moved to another Meal or Day.
- A Dessert Meal.
- A starting Meal guessed from your own Meal windows.
- Trends that bridge gaps, with controls for range, scale, goal line and a second metric.

Guest mode stays. Anyone can try NutriSage without signing in: their data stays on their device
and Bedrock lookups are capped on the server.

## Implementation Decisions

### Platform (parity with HoneyDo)
- **Structure.** A TypeScript npm-workspaces monorepo, rebuilt in the existing repo:
  - `shared`: pure domain logic.
  - `api`: one Node Lambda behind AppSync GraphQL, using Cognito user-pool auth for Members.
  - `web`: React and Vite PWA, with a hand-rolled service worker and runtime config written at deploy time.
  - `infra`: CDK stacks. A Cert stack in us-east-1, an App stack in us-west-1, and a CI stack holding the GitHub OIDC deploy role, which trusts only the `production` environment.
  - Reuse HoneyDo's helpers and patterns before inventing new ones.
- **Old code.** The plain-JS app and the Python backend are deleted only after cutover.
- **Hosting.** A private S3 bucket behind CloudFront with Origin Access Control and a strict CSP and security headers. Served at nutrisage.ashershores.com, a record in the existing ashershores.com hosted zone.
- **Deploys.** Pushing `prod` deploys through GitHub Actions, gated by the `production` environment, which needs Asher's approval. CI actions are pinned to commit SHAs; Dependabot is on.
- **Auth.**
  - Cognito Essentials plan with native passkeys. Allowed first factors are password and passkey; the passkey relying party is the app domain, with user verification required.
  - Self sign-up is off. Two Members (asher, aubyn) are created by an admin script, and the API also checks an allowed-username list.
  - Access and ID tokens last 1 hour; refresh tokens last 7 days. The old shared-secret auth goes away.
- **Guest access.**
  - A Guest uses NutriSage with no sign-in. Guest Days, goals, Favorites and the demo Library live only in browser storage, seeded on first open.
  - The only server call a Guest can make is a nutrition estimate. It goes to a separate, unauthenticated estimate endpoint (not the Member GraphQL API) that cannot read or write the table.
  - The server enforces a per-IP daily cap and a global daily ceiling on Guest estimates, and refuses with a clear "limit reached" error. A per-API throttle, the account Lambda concurrency cap and the budget tripwire stay as outer limits.
  - Any change that exposes this endpoint follows the builder-security policy: anonymous denial of Member data is verified before release.
- **Estimates.**
  - Bedrock runs the latest Sonnet available to the account through a US inference profile. Check availability, and the region it is called from, before wiring it.
  - The estimate returns nutrition for the named serving plus that serving's gram weight. It also returns a Yield ratio when asked about a recipe ingredient.
  - Input length is capped, and responses are parsed leniently: junk numbers become 0, never NaN.
- **Name and region.** NutriSage is the name in the UI, the manifest, stacks and new resources. Everything new lives in us-west-1.
- **Budget.** A $2/month budget on the `app=nutrisage` cost tag.

### Domain model (shared module)
- **Nutrients.** One list shared by every layer: carbs, protein, fat, fiber (g); sodium, iron (mg); calories. Adding a nutrient is a change to that list plus the prompt and the UI.
- **Food.**
  - Fields: id, name, nutrition per gram, named units (each a label plus gram weight, always including "g" and a default "serving"), an optional Yield ratio, and createdBy/updatedAt.
  - Food names are deduplicated case-insensitively when Foods are auto-added.
- **Recipe.**
  - Fields: id, name, ingredients (each a Food or a saved Recipe, one level deep, plus amount and unit), an optional weighed Prepared weight, and createdBy/updatedAt.
  - Derived values:
    - Total nutrition is the sum of the ingredients.
    - Raw weight is the sum of ingredient grams.
    - Prepared weight is the weighed value if set. Otherwise it is estimated as the sum of each ingredient's grams times its Yield ratio, with a ratio of 1 when none is known.
    - Nutrition per prepared gram is total nutrition divided by Prepared weight.
  - A Recipe can be logged without saving; saving it puts it in the Recipe Book (part of the Library).
- **Entry.**
  - Fields: id, Meal, display name, amount, unit, grams (when known), a nutrition snapshot taken at log time, and an optional reference to a Library item.
  - A Recipe Entry also snapshots its ingredient breakdown for the expand view.
  - Library edits and deletes never touch existing Entries.
  - Migrated Entries have a snapshot and a name but no unit or reference.
  - Moving an Entry changes only its Meal and/or Day.
- **Meal.** One of Breakfast, Lunch, Dinner, Dessert, Snack, in that display order.
- **Meal windows.**
  - Each Member sets their own; the defaults are Breakfast before 10:30, Lunch 10:30–14:30, Snack 14:30–17:00, Dinner 17:00–20:30, Dessert from 20:30.
  - The guess uses the device's local time and runs on app open and when the date rolls over.
  - A manual pick lasts until the app is reopened.
- **Amount parsing.** Accepts decimals, simple fractions and mixed numbers. Valid range is greater than 0 and at most 100; anything else is rejected with a message, not silently reset.
- **Favorites and Quick Add.**
  - A Favorite is a per-Member record holding a Library item reference and a last-used time.
  - Quick Add is the Member's Favorites sorted by last used, newest first. Logging a starred item from anywhere bumps its last-used time.
  - Deleting a Library item removes the Favorites that point at it.
- **Fuzzy search.**
  - Client-side over the Library: typo-tolerant, partial-token matching, with Favorites boosted.
  - When nothing scores above a threshold, Enter means "estimate as a new Food".
  - The ranking is a pure function so it can be tested.
- **Trend series.**
  - A pure function from Days, a metric, a range and a bucket size to points. Unlogged Days become no-data, not 0, and segments that cross missing Days are flagged as bridged.
  - Ranges over about 90 days are bucketed weekly, averaging logged Days only. Today is flagged as in progress.
  - Y-axis bounds are computed for fit, zero-based or manual mode, and a second series gets its own bounds.
- **Kept as-is from the current app.**
  - Pure helpers (moved into the shared module): week stats (averages over logged Days, totals against goal x7), streak (an unlogged today doesn't break it), bar percentages, and the carbs/fat "shared energy pool" bar coloring.
  - Unchanged features: water cups against a water goal, once-per-Day weight, light/dark/system theme.

### Data (one DynamoDB table, HoneyDo pattern)
- **Table.** One table with keys `PK`/`SK`, on demand, with point-in-time recovery, deletion protection and RETAIN.
- **Items:**
  - Per-Member partition: Day rows keyed by date (`DAY#YYYY-MM-DD`), plus goals, Meal windows and Favorites.
  - One household partition: Library rows (`FOOD#id`, `RECIPE#id`).
- **Writes.** Write-through from the client's local copy via an outbox, so offline works. Conflicts resolve last-write-wins per Day row; a Day write always carries the whole Day (Entries, water, weight).

### API contract (GraphQL, Members only)
- **Queries:** a Member's Days for a date range, goals and Meal windows, Favorites, and the full Library.
- **Mutations:** put Day, put goals and Meal windows, put or delete Favorite, put or delete Food or Recipe, and estimate. Estimate is also on the Guest endpoint, with caps.
- **Validation and limits.** Server-side checks cover nutrient numbers (finite, ≥ 0), amounts, payload size and record caps. Unknown usernames are refused even with a valid token.

### Migration and cutover
- **Migration script.**
  - A one-time script exports asher's and aubyn's rows plus the household quick-add meals from the old table.
  - Tommy's data is not migrated.
  - It maps them into the new model:
    - Days and their Entries become snapshot Entries, with old "snack" and missing Meals kept as Snack.
    - Goals, water and weight carry over.
    - Favorites become Foods plus Favorites; the old 1× nutrition is treated as one serving with unknown grams.
    - Old quick-add meals become Foods.
  - It is idempotent and dry-run first, printing counts to compare.
- **Cutover order.**
  1. Deploy the new app.
  2. Migrate.
  3. Asher checks his history.
  4. Rename the GitHub repo to NutriSage (not before, because the old Pages URL path depends on the repo name).
  5. Point GitHub Pages at a redirect page.
  6. Update the App Connector Tile.
  7. Later, with Asher's go, retire the old us-east-1 Lambda, API, table and role.

### Milestones
- **M1, platform parity.** Stack, sign-in, Guest with server caps, migration, and the current features working. Also: the Dessert Meal, Meal windows, decimal/fraction amounts with a unit picker, moving an Entry between Meals and Days, and Entry snapshots.
- **M2, Library.** Library with auto-add, fuzzy search, Favorites and Quick Add, per-gram Foods with units, and Library editing.
- **M3, Recipes.** Recipe builder, Recipe Book, Prepared weight (weighed or estimated from Yield ratios), Recipe Entries with breakdown, and one level of nesting.
- **M4, Trends.** Gap bridging, range presets and custom range, weekly buckets, Y-axis modes, goal line, and a second metric.
- **Shipping.** Each milestone is its own PR to `main`, then a `main`→`prod` deploy.

## Testing Decisions

- **What a good test is.** Tests check behaviour you can see from outside a module (inputs to outputs, API requests to responses and stored state, screens and clicks), never internal structure. Any new pure logic gets a test in the shared module.
- **Seam 1: shared domain module (vitest).**
  - Amount parsing: fractions, mixed numbers, bounds.
  - Unit and per-gram scaling.
  - Recipe totals, Prepared weight (weighed vs Yield-ratio estimate) and per-portion nutrition (grams and fraction of batch), plus nesting limits.
  - Meal window guess, including boundaries and custom windows.
  - Quick Add ordering and bumping.
  - Fuzzy ranking: typos, partial tokens, Favorite boost, the "no match" threshold.
  - Trend series: no-data gaps, bridged flags, weekly buckets, in-progress today, Y-axis bounds for each mode and the second axis.
  - Week stats, streak, bar state and energy pool, ported with the current cases.
  - Prior art: HoneyDo `shared` tests and the current `macros.test.js` cases.
- **Seam 2: API handler on the fake-DynamoDB harness (vitest), with Bedrock stubbed.**
  - Member-only access and the username allowlist.
  - Each Member reads and writes only their own Days, goals and Favorites; the Library is shared.
  - Guest endpoint caps: per-IP, global ceiling, refusal message. Guests can't reach table data.
  - Validation and record caps.
  - Library delete cascades to Favorites and leaves Entries alone.
  - Migration mapping, run against a fixture export of the old rows.
  - Prior art: HoneyDo `api` tests and testing harness.
- **Seam 3: Playwright e2e against the in-process fake backend, plus a visual screenshot tour (phone, desktop, dark).**
  - Logging with a guessed Meal; editing amounts with fractions; moving an Entry; Quick Add bump; search-then-estimate.
  - Building, saving and logging a Recipe by grams and by fraction.
  - Trends controls; Guest flow.
  - Screenshots are looked at, not just DOM-checked.
  - Real passkeys can't be automated: verify on device after deploy.
  - Prior art: HoneyDo e2e lib/backend and tour.
- **Before deploying.** Full tests, typecheck, build and synth run before each PR. Infra changes get a `--no-execute` change set checked for replacements. After deploy, confirm the live bundle hash matches the local build.

## Out of Scope

- Barcode scanning, nutrition-label photo OCR, and external food databases (USDA, etc.).
- Live links from Entries to Library items: edits never recalculate history.
- Recipe nesting deeper than one level.
- Per-Member private Libraries, and Guests reading the household Library.
- Tommy's profile and data; self sign-up; more than two Members.
- Passkey-only sign-in (password stays as backup).
- Push notifications or reminders.
- Learning Meal windows from history (windows are set manually).
- Drag-and-drop to move Entries (editor picker only).
- Renaming the old us-east-1 resources: they are retired, not renamed.
